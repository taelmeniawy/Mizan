# ADR-0002 — قاعدة البيانات وسلامة البيانات

| البند | القيمة |
|---|---|
| المعرّف | `ADR-0002` |
| العنوان | SQLite، المعاملات، القيود، الترحيلات، والنسخ الاحتياطي |
| الحالة | **PROPOSED / NEEDS APPROVAL** |
| التاريخ | نوفمبر 2026 |
| يؤثر على | المحاسبة، المخزون، الترحيل، النسخ، الاستعادة |
| لا يغطيه | اختيار UI (ADR-0001)، دقة المال (ADR-0003)، محرك A4 (ADR-0004) |

> SQLite **مرشحة**، وليست معتمدة. أي تنفيذ قبل اعتماد ADR-0001/0002 يخالف قواعد Batch 1.

## 1. السياق

- تطبيق Windows Desktop، جهاز واحد، متجر واحد، مخزن واحد.
- عمل offline، بيانات محلية.
- معاملات مالية/مخزنية تحتاج ذرية وقيودًا.
- مستخدم واحد فعليًا في كل وقت، مع احتمال جلسات متعددة/نوافذ.
- حجم بيانات صغير/متوسط (عشرات آلاف الأصناف، ملايين الحركات لاحقًا).
- نسخ احتياطي/استعادة موثوقان.
- لا خدمة DB منفصلة/إدارة خادم.
- لا native decimal؛ ADR-0003 يعالج.

## 2. الخيارات

### الخيار A — SQLite (موصى به مبدئيًا)

**المزايا:**

- ملف/قاعدة محلية بلا خادم؛ مناسب لجهاز واحد/offline.
- معاملات ACID، FKs، فهارس، triggers، partial indexes.
- Online Backup API.
- تكلفة تشغيل/تثبيت منخفضة.
- نضج/دعم واسع.

**العيوب/المخاطر:**

- كاتب واحد في كل وقت (WAL يحسّن القراءة).
- لا native decimal.
- إدارة الملف/النسخ/التزامن مسؤولية التطبيق.
- `busy_timeout`/معاملات طويلة قد تسبب أخطاء.
- النسخ الملفي أثناء التشغيل غير آمن كافتراضي.
- لا أدوار/أمان على مستوى الخادم.

### الخيار B — PostgreSQL/خدمة محلية

**المزايا:** تعدد كتابة/concurrency، decimal، أدوات، أمان.
**العيوب:** خدمة/تثبيت/صيانة/موارد؛ تعقيد offline؛ لا يتناسب مع V1 البسيط. يمكن اعتباره لاحقًا عند التوسع.

### الخيار C — قاعدة مدمجة أخرى (LiteDB/DuckDB/…) 

**المزايا:** خفة/تحليلات.
**العيوب:** نضج أقل للمعاملات المالية/القيود/النسخ، أو توجه تحليلي لا OLTP. لا تُعتمد دون تقييم.

### الخيار D — ملفات/JSON

**مرفوض** للمعاملات المالية: لا ACID/قيود علائقية كافية، ويصعب التدقيق.

## 3. القرار المقترح

**SQLite في وضع WAL، مع:**
- `PRAGMA foreign_keys = ON` في كل اتصال.
- `PRAGMA journal_mode = WAL`.
- `PRAGMA synchronous = FULL` أو `NORMAL` مع WAL — **يُختار بعد اختبار متانة/أداء**.
- `PRAGMA busy_timeout` مناسب (مثل 5000ms؛ القيمة النهائية تُختبر).
- `PRAGMA wal_autocheckpoint`/checkpoint دوري.
- معاملات `BEGIN IMMEDIATE` للكتابة الحرجة.
- اتصال كتابة واحد/تسلسل على مستوى التطبيق.
- قيود/FKs/فهارس/partial indexes.
- Online Backup API/آلية متسقة.
- فحص `integrity_check`/`foreign_key_check` دوري.

### 3.1 لماذا `BEGIN IMMEDIATE`؟

لتقليل ترقية القفل من قراءة إلى كتابة في منتصف المعاملة، وتقليل `SQLITE_BUSY`/فشل الترحيل. المعاملة قصيرة، وتشمل القيد/المخزون.

### 3.2 التزامن

- V1: مستخدم/جهاز واحد، لكن قد توجد نوافذ/عمليات خلفية (نسخ/تقارير).
- اتصال كتابة واحد + قائمة انتظار داخل التطبيق.
- القراءات يمكن أن تستخدم اتصالات قراءة/WAL.
- لا تُفتح معاملات طويلة أثناء حوارات المستخدم.
- النسخ/التقارير الثقيلة لا تحجب الكتابة لأكثر من اللازم.

### 3.3 المال والكمية

- `INTEGER` للقرش/الكميات/الأسعار (ADR-0003).
- لا `REAL`/`NUMERIC` للحقول الحسابية.
- قيود CHECK على non-negative/one-side.

### 3.4 المفاتيح والقيود

- FKs مفعلة، مع `ON DELETE RESTRICT` للبيانات التاريخية (لا حذف مستند/دفعة مستخدمة).
- Partial unique لمنع تحويل العرض المكرر.
- Triggers للمنع المتقاطع (lot/reel) حيث لا يكفي CHECK.
- لا تعتمد على التطبيق وحده في القيود الحرجة.

| المعرّف | القاعدة | الحالة |

| DB-MIG-002 | نسخة احتياطية قبل migration في الإنتاج. | CONFIRMED (حماية) / PROPOSED (آلية) |
| DB-MIG-003 | migration قابلة للتطبيق على DB موجودة، ومختبرة على نسخة. | PROPOSED |
| DB-MIG-004 | لا تعديل يدوي لمخطط الإنتاج. | PROPOSED |

- أدوات: Alembic/EF Core Migrations (حسب ADR-0001).
- لا تُنشأ migrations في Batch 1.

## 5. النسخ الاحتياطي

### 5.1 النهج

- **Online Backup API** أو آلية متسقة مكافئة.
- **لا** يُستخدم نسخ ملف قاعدة حيّة كافتراضي.
- يشمل:
  - قاعدة البيانات.
  - ملفات PDF/المستندات.
  - manifest/baselines/hash.
- تحقق من `integrity_check` و`foreign_key_check` وبصمات الملفات.
- نسخة محلية + خارج الجهاز (حسب `OQ-BKP-001`).
- تشفير/مفتاح منفصل (PROPOSED/`OQ-BKP-002`).
- الاحتفاظ 30 يومية/12 شهرية/قبل التحديث (PROPOSED).
- لا تُحذف النسخ القديمة قبل نجاح الجديدة.

### 5.2 الاستعادة

1. التحقق من manifest/hash.
2. فحص DB.
3. استعادة إلى مجلد مؤقت.
4. فحص التكامل.
5. استبدال/فتح النسخة.
6. اختبار دخان (فتح/تقرير/مستند).
7. توثيق العملية.

- الاستعادة ليست مجرد «نسخ ملف»؛ يجب التحقق.
- اختبار استعادة دوري على جهاز/مجلد منفصل.

## 6. الاستعادة من الفشل

| السيناريو | الاستجابة |
|---|---|
| انقطاع كهرباء/إنهاء مفاجئ | WAL + معاملات تعيد الحالة; فحص عند البدء |
| `SQLITE_BUSY` | إعادة محاولة محدودة + رسالة |
| ملف تالف | فحص، استعادة من نسخة، لا إصلاح صامت |
| فشل migration | rollback/استعادة نسخة قبلية |
| فقدان ملف PDF | كشف/استعادة، لا إعادة إنشاء رسمي |
| تعارض كتابة | تسلسل/رفض واضح |

- لا يُصلح التطبيق DB تلقائيًا بإسقاط بيانات.
- لا تُتجاهل أخطاء القيود.

## 7. الأمن

- SQLite لا تفرض صلاحيات مستخدم DB؛ التطبيق يفرض الصلاحيات.
- الملفات المحلية تحت حماية حساب Windows؛ التشفير at-rest **PROPOSED/OPEN**.
- النسخ مشفرة (PROPOSED).
- لا تُخزَّن كلمات المرور/المفاتيح في DB كنص.
- صلاحية الوصول لمجلد البيانات/النسخ مقيدة.

## 8. Consequences

### إيجابيات

- بساطة النشر/offline.
- معاملات/قيود كافية للنواة.
- نسخ/استعادة ممكنان.
- لا خادم/صيانة.

### تكاليف/قيود

- كاتب واحد؛ يجب تصميم التزامن.
- لا decimal؛ أنواع integer مخصصة.
- النسخ/الاستعادة مسؤولية تطبيق.
-Triggers/Partial indexes تحتاج اختبارًا.
- التوسع لاحقًا إلى multi-device/فرع يحتاج إعادة تقييم (خارج V1).

## 9. ما يجب التحقق منه قبل التنفيذ

| # | التحقق | معيار النجاح |
|---:|---|---|
| 1 | WAL/synchronous/busy_timeout | سلوك مستقر تحت كتابة/قراءة متزامنة |
| 2 | FKs | مرجع غير موجود مرفوض |
| 3 | معاملة ترحيل | rollback كامل عند فشل القيد/المخزون |
| 4 | Partial index | منع التحويل المكرر على مستوى DB |
| 5 | Triggers | منع lot/reel المزدوج |
| 6 | Online Backup | نسخة أثناء التشغيل + استعادة ناجحة |
| 7 | Integrity | كشف تلف/فشل FKs |
| 8 | Migration | ترقية DB موجودة دون فقدان |
| 9 | الأداء | معاملات/pagination/فهارس مقبولة |
| 10 | التشفير | استعادة بمفتاح صحيح فقط (إن اعتُمد) |

## 10. القرار

**الحالة: NEEDS APPROVAL.** التوصية: SQLite/WAL/FKs/معاملات ذرية/Online Backup، مع عدم اعتبارها نهائية قبل اعتماد المالك وتجربة الاستعادة. لا تُنشأ قاعدة بيانات في Batch 1.
